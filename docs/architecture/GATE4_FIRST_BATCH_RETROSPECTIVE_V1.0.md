# Gate 4 第一批四页执行复盘 V1.0

日期：2026-09-07。复盘对象：`G4-13PAGE-BATCH4-01` 第一批 Germany、Italy、Coatings、Plastics。状态：`RETROSPECTIVE_COMPLETE / PROCESS_CHANGE_NOT_YET_APPROVED`。

本记录只分析已完成成果和流程效率，不改变四页 Gate 4 关闭状态，不启动后续页面或 Gate 6。

## 1. 结论

第一批从批次控制建立（15:30:30）到完成记录生成（16:52:10）共 81 分 40 秒。结果质量合格，但执行成本明显过高。

直接原因不是四页视觉反复失败。四个最终 HTML 均保持首次冻结后的源身份；Italy、Coatings、Plastics 的 Required Finding 都是证据元数据或证据陈述问题，而非页面视觉返工。主要耗时发生在重复生成证据、独立审查重新渲染、总控再次逐项复算，以及由记录缺陷触发的新冻结和复审。

流程在职责上已合并 Gate 4/5，但实际操作仍保留了原两阶段叠加的证明强度，并额外形成“执行自检—独立审查—总控深度复算”三层近似重复验证。这是本批耗时的核心问题。

## 5. 根因

### 5.1 最低证据被执行成全量证据

现行规则要求三端整页、长页可读检查和适用状态，但没有要求把每次诊断、每个分段、每次预检都永久保存。执行中把“必须覆盖”解释成“必须为每项长期保存独立图片和身份记录”，导致证据数量膨胀。

### 5.2 独立审查重复生产执行证据

`layout-interaction-verification` 已规定：默认直接审执行方正式核心图；只有来源可疑、渲染不一致、发现 Finding 或任务明确要求时，才长期保存整套独立重复栅格图。本批 Germany、Italy、Coatings、Plastics 首审仍分别进行了大规模独立重渲染。执行偏离了方法中已有的复用原则。

### 5.3 冻结前没有统一机器门禁

每页使用不同 JSON 结构、字段命名和页面专属脚本。物理尺寸、逻辑尺寸、DPR、状态、bytes、SHA 的规则没有由一个共享 validator 强制执行。结果是页面视觉已完成后，因为台账字段错误重建 workset、freeze、evidence index、提交、复审和关闭记录。

### 5.4 总控边界过深

总控本应核对执行/审查角色分离、冻结身份、Finding 状态、合同冲突和关闭条件。本批总控对部分页面重新计算了大量图片与记录，实质上成为第二独立审查层。这样既延长关键路径，也让“独立审查 PASS”缺少明确终局含义。

### 5.5 诊断历史没有收敛规则

Coatings 多轮 preflight 每轮保存 34 张可读分段；其他页面也保存执行截图、审查截图、contact sheet、readback 和 identity audit。规则要求保留历史，但没有在同一轮中明确哪些是失败历史、哪些只是可丢弃的临时采集，导致每次运行都变成正式资产。

### 5.6 并发批次与运行槽不匹配

当前运行上限是 root 加 3 个子代理。所谓“一批四个”实际是 3 个并发执行加 1 个排队页面。进入独立审查后，还要满足执行者与审查者不同，三个子代理在执行、互审、返修之间切换，关键路径由最晚页面和最晚 Finding 复审决定。

### 5.7 把可变导航文件纳入冻结身份

Germany 和 Coatings 审查期间，根 `01_PROJECT_INDEX.md` 因其他任务更新而产生哈希漂移，虽然最终确认与页面合同无关，仍触发了额外快照、比对和说明。根索引是导航文件，不适合作为页面冻结的阻塞身份；真正需要冻结的是它指向的具体批准合同。

## 6. 哪些控制必须保留

- 一个 Gate 4 执行 Agent 对 4A、完整页面、返修和冻结端到端负责。
- 1440、768、390 三端完整页面必须检查。
- 长页必须以可读方式覆盖，但可使用临时分段、contact sheet或查看工具，不要求全部成为 approval core。
- 页面适用的 Menu、Cookie、CTA、焦点、hover、表单等状态必须检查。
- 执行者与最终独立审查者必须不同。
- Finding 修正后必须按变化范围独立复验。
- 冻结源、耐久依赖、正式证据和审查报告必须有可验证身份。
- 总控必须核对关闭条件，但不重复承担独立审查。

## 7. 建议的新执行模型

### 7.1 冻结前增加一个共享 validator

统一脚本从实际文件读取 PNG 宽高、bytes、SHA 和 DPR，验证必填字段、路径、workset/freeze 关系及重复资产。validator 未通过不得提交独立审查。Italy 和 Plastics 的元数据问题应在这里直接拦截。

### 7.2 收紧 approval core

每页默认长期保存：

1. 三张完整页面图；
2. 一套能覆盖长页阅读的 contact sheet 或必要分段索引；
3. 每类高风险组件在有差异的视口/状态证据；
4. 一份运行观察 JSON；
5. 一个证据索引。

同一规则下重复的普通状态可由运行测量和抽样图证明。失败截图、重复预检图、临时分段默认留在工作临时区；确有 Finding 时只把相关证据纳入诊断历史。

### 7.3 独立审查采用“复算身份＋风险抽样＋实际操作”

独立审查者应：

- 自动复算全部核心文件身份；
- 打开执行方三端整页和 contact sheet；
- 独立运行页面并操作高风险路径；
- 默认只重渲染三端整页或少量高风险状态；
- 只有出现来源可疑、视觉差异或 Finding 时才扩展重渲染范围。

这样仍保持独立判断，但不复制执行方的 42–89 张整套证据。

### 7.4 定向复审严格按变更影响

若 HTML/CSS/依赖哈希未变，只修 evidence metadata，则复审应验证：修正字段、相关文件真实元数据、全部索引闭合和少量读回样本。无需重新打开或重渲染 56/92 张未变图片。若视觉源改变，再执行受影响视口、状态和相邻回归。

### 7.5 总控只做关闭审计

总控使用固定清单核对：授权、角色分离、validator PASS、独立报告身份、Required Finding=0、合同冲突、冻结组合、Manifest 和停止边界。没有漂移证据时，不重新逐图复算或重新进行视觉审查。

### 7.6 使用共享工具，不再每页复制脚本

renderer、PNG identity validator、evidence-index builder、contact-sheet builder 和 closure validator 应各有一个共享版本。页面只保存配置和结果，不复制 9–15 个脚本。这样可减少字段漂移和不同页面各自修复相同工具问题。

### 7.7 批次按三个并发槽设计

在当前运行限制下，默认一波三个页面。完成执行后交叉互审；root 只做调度和关闭审计。若业务上仍称四页一批，应明确第四页是下一波首项，不能把它描述为四页同时执行。

### 7.8 冻结具体合同，不冻结可变导航

根 Index、Status 等导航/进度文件只记录读取时版本和解析出的目标，不作为页面冻结阻塞输入。页面冻结直接绑定 Brief、批准内容、Gate 3、品牌、共享 owner 和决定文件的精确身份。

## 8. 预期效果与衡量方式

下一批应记录以下效率指标，用真实结果决定是否继续调整：

- 从授权到 `COMPLETE_VISUAL_FROZEN` 的时间；
- 从冻结到独立 PASS 的时间；
- 每页 approval-core PNG 数量；
- 独立审查新增 PNG 数量；
- 因 schema/身份问题返修次数；
- HTML/CSS 未变但重新渲染的图片数量；
- 总控关闭耗时。

首轮目标应是：schema/身份类 Finding 在提交前归零；独立审查不再复制整套栅格证据；总控不再进行第二轮完整审查；同一未变图片只保存一个正式身份。达到这些条件后，再用下一批真实耗时评估是否把墙钟时间压缩约一半。

## 9. 责任判断

这次耗时不是用户审核造成，也不是因为四个页面本身质量差。主要责任在流程执行设计和本次总控：虽然规则已经写了复用、按风险、避免重复，但派发与验收没有设置证据上限、共享 validator 和清晰的总控边界，导致子代理采取最保守的全量证明方式。并行子代理加快了制作，却放大了不同证据格式和重复渲染的成本。

四页现有关闭结论仍可靠；问题在于取得这些可靠结论的路径过重。后续若获准继续，应先修订 Gate 4 Agent、共同合同、三项 Skill 和批次模板，再执行下一批。
