## 2. 执行边界

- 当前流程按`Gate 0→1→2→3→4→6→8→9→10`解释；DOC-COO与PRODUCT-PROC-CL历史Gate 5完整视觉批准映射为当前Gate 4成果，历史文件名和批准身份保留。
- 本轮可形成综合审查草案、唯一开发交付包草案、稳定Gate 9接受条件和页面Manifest状态更新。
- 本轮未授权向开发任务实际发送、Gate 8实现、D16读取或写入、部署、发布、DNS或索引。
- 本轮由同一Gate 6总控整理新增交付合同，因此只能对新包做自检；不能把自检记为独立项目控制PASS。四包在不同审查者复核前保持`DRAFT_FOR_PROJECT_CONTROL_REVIEW`。
- 上游Gate 4最终独立审查按精确冻结身份继承；只有冻结后变化、未覆盖缺口或跨合同冲突触发定向复核，不重复整套视觉验收。

## 3. 方法和判断口径

本轮使用当前Gate 6 Agent V0.4、页面合同一致性核验V0.2和开发交付规格整理V0.2。每页必须：

- 绑定唯一当前Manifest、B/C正文与行为源、完整冻结原型、依赖和批准证据；
- 区分“原型已修订”“交付合同已澄清”和“生产实现已验证”；
- 把共享owner、当前运行记录和未来依赖关联到稳定Gate 9 ID；
- 不猜WordPress post type、API字段、组件路径、数据库、缓存实现或新接收接口；
- 允许Gate 8核对现有项目后复用或改造原型，但不承诺原型可直接合并；
- 只有实际实现、指定环境和对应业务证据才可满足Gate 9，包内一致性检查不得预签通过。
