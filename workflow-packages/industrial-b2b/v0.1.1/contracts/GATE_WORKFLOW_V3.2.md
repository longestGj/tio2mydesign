母版版本：0.1.0（提取候选，尚未安装/发布验证）。运行前读取[实例绑定合同](instance-bindings.md)；本站事实、授权与进度不随方法复制。

## 2. 当前阶段

`W1 → W2 → W3 → W4 → W5 → Gate 0 → 1 → 2 → 3 → 4 → 5（独立视觉审查）→ 6 → 8 → 9 → 10`

| Gate | 名称 | 职责与结果 |
|---|---|---|
| 0 | 任务准入 | 页面登记、身份、范围与任务输入 |
| 1 | 研究与意图确认 | 买家问题、证据、方向及页面职责 |
| 2 | 完整内容与模块确认 | 真实正文、行动、SEO/GEO/Schema语义和内容合同 |
| 3 | 响应式线框 | 完整内容的三端结构与适用交互位置 |
| 4 | 完整视觉设计与验证 | 视觉方向、三端整页、全部内容实例、适用关键状态、冻结证据与最终独立审查 |
| 5 | 独立视觉审查 | 承接Gate 4唯一最终独立审查；按4→5合同与同一视觉组合关闭，不增加审批轮次 |
| 6 | 策划总审与开发交付 | 检查全部策划成果一致性、关闭合同冲突、形成唯一开发交付入口与Gate 9接受条件 |
| 7 | 历史编号；不再单独执行 | 原策划交付职责并入Gate 6 |
| 8 | WordPress＋Next.js外部开发 | 技术承接、实现、测试、回执与修复 |
| 9 | 只读质量验收 | 对指定开发实现独立核验批准合同 |
| 10 | 发布授权 | 用户另行批准后执行发布相关操作 |

保留5、7、8、9、10编号以维持历史记录和开发合同可追溯性。当前4→6、6→8均为正常衔接，不算跳过有效阶段。

## 3. Gate 4：完整视觉设计与验证

### 3.1 单一责任与共同工作集

一个Gate 4执行Agent端到端负责视觉方向、完整页面应用、核验、返修、冻结和提交。三个能力Skill维护各自方法，不取得页面授权或阶段批准权：

1. `brand-applied-visual-design`：形成视觉规则并用真实高风险样例验证。
2. `full-page-visual-composition`：把已通过4A检查的方向应用到全部页面实例、三端整页及适用状态。
3. `layout-interaction-verification`：核验内容可见性、响应式几何、状态外观和可实际操作的本地行为。

三者使用同一工作集ID、同一设计源、同一输入清单和同一证据索引。后续方法读取前一方法已经核验且身份未变的共同输入，不重复整理全文、重复导出相同资产或另建竞争报告。每项方法只追加自身产物、观察、Finding与未验证范围；执行Agent负责综合。

### 3.2 4A内部检查点

`VISUAL_DIRECTION_CHECKED`是Gate 4内部检查点。它确认视觉重点、品牌用途、信息密度、组件外观、媒体规则和关键响应式风险足以继续整页制作。

4A不是独立Gate，不产生`APPROVED / CLOSED`，也不要求一次单独的用户方向批准。既有方向、家族规则和共享合同足以裁决时，Agent完成检查即可连续进入完整页面制作。出现重大新品牌方向、共享owner变化、内容/结构冲突或超出当前授权的选择时，只提交受影响决定；其余工作可继续。

`full-page-visual-composition`的方向输入必须写为“已通过4A检查的视觉方向，以及相关已批准品牌、文案、结构和共享组件合同”，不得继续要求一个独立Gate 4批准作为启动前提。

### 3.3 4B唯一正式关闭点

`COMPLETE_VISUAL_FROZEN`表示三端完整页面、适用状态、源与依赖已形成可审冻结组合；它仍不是阶段批准。

冻结后只设置一个Gate 4最终独立审查环节。该环节可以产生Finding、返修和多次定向复审；“一个环节”不表示只能检查一遍。最终审查对象包括：

- 批准内容和结构是否完整、准确呈现；
- 视觉是否符合品牌、共享owner和本页任务；
- 1440、768、390完整页面及长页连接是否成立；
- Mobile Menu与页面适用状态是否覆盖；
- 静态外观、实际本地操作、源码观察和模拟证据是否正确区分；
- 版本、依赖、冻结身份、开放项与历史关系是否可追溯。

Finding关闭并经总控依据本站有效授权核对后，记录`Gate 4 APPROVED / CLOSED`。4A没有单独关闭状态；4B是唯一正式关闭点。

### 3.4 一个权威入口

“一套成果”指一个权威入口和一个冻结组合，不要求一个物理文件。当前Manifest指向：

- 可编辑设计源及其耐久依赖；
- 共享组件、字体和媒体的精确owner引用；
- 1440、768、390三张完整页面基础证据；
- 长页所需可读分段与适用菜单、表单、Cookie等状态证据；
- 对应实际操作证据及其`ACTUAL_RUNTIME`、`STATIC_VISUAL`、`SOURCE_INSPECTION`或`LOCAL_SIMULATION`类别；
- 自检、最终独立审查、Finding/复审和批准记录。

截图证明外观，不自动证明交互行为；策划阶段本地运行或模拟不代替Gate 9对开发实现的验证。Gate 4→6接收文件保持简短，只提供权威入口、适用范围、相对上游的变化、开放项和冻结身份，不复制全部合同。

## 4. Gate 6：总审与Gate 4的边界

Gate 4最终独立审查判断完整视觉是否符合批准内容、结构、品牌、响应式和状态要求。Gate 6判断Gate 1–4全部策划成果是否一致、开发交付是否明确、Gate 9是否具备可执行验收依据。

Gate 6必须引用有效Gate 4审查证据，并按变化、缺口和合同冲突进行复核；没有新证据、身份变化或冲突时，不重做整套视觉验收。若Gate 6发现实际视觉缺陷或冻结组合失配，定向退回Gate 4并按新身份复审。Gate 6自身新增的开发映射与验收合同仍需独立核对。

Gate 6继续负责唯一交付包；正文保持唯一编辑源，交付入口用引用和差异说明组织。Gate 6批准不自动授权Gate 8、开发、派发或发布。

## 5. Gate 8、Gate 9与Gate 10

Gate 8在独立开发项目中完成技术承接、WordPress/API/Next.js映射、实现、测试和回执。策划侧不进入开发侧执行这些工作。

Gate 9锁定Gate 6批准包、开发版本和可访问结果，独立核验内容、三端视觉、状态、实际交互、SEO/GEO/Schema、数据来源、共享消费与`site_scope=${site_scope}`隔离。Gate 4的策划模拟不能代替开发运行证据；开发自检也不代替Gate 9。

Gate 10及生产部署、域名、DNS、索引和对外发布继续需要用户单独明确授权。

## 6. 历史与在途兼容

| 历史或在途状态 | 当前处理 |
|---|---|
| 旧Gate 5已获用户批准 | 核对批准范围、对应版本和冻结身份后，登记为新Gate 4完整关闭；不重新审批、不重做资产 |
| 旧Gate 4已批准、旧Gate 5未完成 | 继承有效方向和已有证据，只补三端整页、适用状态、冻结与最终独立审查的实际缺口 |
| 旧Gate 4/5均未开始 | 使用新Gate 4完整流程 |
| 旧Gate 5候选或在途 | 按已有授权边界映射到4B工作；原授权没有覆盖完整视觉时不得自动扩张 |
| 旧Gate 4/5文件、Review ID、hash和Manifest字段 | 保留历史名称与语义；新Manifest通过映射引用，不全局改名 |

成果映射不等于继续执行授权。流程批准只允许更新项目治理和方法源，不能自动恢复暂停任务、启动下一页或扩大页面阶段权限。

## 7. 当前状态与授权定义

Gate 4可使用以下状态：

`NOT_STARTED / NOT_AUTHORIZED`

→ `USER_AUTHORIZED / IN_PROGRESS`

→ `VISUAL_DIRECTION_CHECKED`（4A内部检查点）

→ `COMPLETE_VISUAL_FROZEN / DRAFT_FOR_PROJECT_CONTROL_REVIEW`

→ `PROJECT_CONTROL_REVIEW_PASS`

→ `APPROVED / CLOSED`

返修与复审保留稳定Finding ID并绑定新冻结身份，不另造阶段。Manifest分别记录生命周期、4A检查、冻结、最终审查、总控关闭依据、下一阶段授权和外部实施状态，不能用其中一项替代另一项。

## 8. 决定留痕
按本站真实用户决定记录日期、对象、范围、来源；包版本与页面批准分别记录。

## 9. 按阶段消费输入与控制重复工作

从根AGENTS和PROJECT_CONTEXT进入，经Index取得当前流程、适用标准、对应角色与方法基线；页面任务再取得当前Manifest、原始授权及批准上游。只读本阶段所需范围，实际读过且身份未变的输入可复用；首次读取不能用摘要或“之前的Agent读过”代替。

| 阶段 | 当前应解决的问题 | 有效上游怎样消费 | 结束依据 |
|---|---|---|---|
| Gate 1 | 本页买家问题、搜索意图、证据与职责 | 复用全站已有研究，只补本页缺口 | 意图与研究成果按既有审查及批准流程确认 |
| Gate 2 | 完整文案、模块顺序与行为/机器语义 | 使用有效研究和事实决定 | 保留骨架→Full Copy两步，以及完整独立Buyer Review、返修复核与总控复核；按有效用户授权关闭 |
| Gate 3 | 完整内容三端结构、关系与可操作性 | 使用真实批准正文及符合资格的共享验证 | 按统一标准§4.3完成结构检查、冻结、独立审查与批准；纯视觉建议转Gate 4 |
| Gate 4 | 视觉方向及完整三端、状态和全部实例 | 消费Gate 3结构约束；同一工作集连续4A→4B | 完整冻结后一个最终独立审查环节及总控依授权关闭 |
| Gate 6 | 跨合同一致性、开发交付与可执行验收要求 | 引用有效Gate 4审查；只按变化、缺口、冲突展开复核 | 问题关闭，唯一交付组合、新增合同独立复核及相应批准 |
| Gate 8 | 现有WordPress＋Next.js系统中的技术承接与实现 | 读取批准包及已有页面/共享能力的实际集成基线 | 指定实现版本、测试证据与开发回执；代码工作归开发项目 |
| Gate 9 | 实际实现是否兑现批准合同 | 开发自检作输入，策划截图/模拟作对照 | 对准确实现独立只读验证，Finding按新版本定向复验及关联回归 |

每份额外报告、状态图、重导、检查或返修都应对应具体合同要求、变化、缺口或风险；不设图数/轮次配额，不为相同身份与相同证明对象重复生成证据。该原则不减免已批准最低证据、完整内容扫描、适用状态、独立审查或明确页面专属要求。

先归属问题，再决定是否阻塞：文字/事实/行为语义归原内容owner；结构与响应关系归Gate 3；完整视觉归Gate 4；跨合同与交付缺口归Gate 6；实现归Gate 8、结果验证归Gate 9。纯视觉偏好不阻塞Gate 3，正常未来运行依赖不自动阻塞策划；缺少明确行为、owner或接受条件的依赖、真实合同冲突不能一律推给未来。

同一页面维持一个当前Manifest和一个正文编辑源。交接以精确引用、差异和开放项组织；确需完整payload时由批准源受控派生并逐项映射，不独立编辑成第二套正文。内部检查点不重复索取已有授权；连续授权只在原对象、范围与条件内生效。不得以“减少重复”为由撤销Gate 2独立Buyer Review或Gate 9对实际实现的独立验收。

## 10. WordPress＋Next.js承接与同合同验收

Gate 6交付说明页面需要管理、显示和执行的结果，标明共享owner、已知既有页面依赖、条件/空值/失败行为与scope隔离；不凭空决定post type、API名或组件路径。已有技术合同按批准范围继承。

Gate 8开发方先核对实际代码/工作区是否包含已整合的页面、内容模型、API、共享组件和站点能力，确定复用、扩展与必要新增；不因错误或陈旧基线缺少能力而另建平行系统。技术映射覆盖WordPress→API→Next.js、路由、元数据、缓存、菜单、表单和媒体，并确定受影响已有页面与跨scope回归。改变批准语义或共享合同须返回原owner；普通技术选择由开发方完成。

同一接受条件ID贯穿Gate 6→8→9。开发回执绑定commit/ref与工作区状态、环境、数据来源、实现位置、测试结果、适用视口/状态、差异、未测项和回退说明。Gate 9独立核对全量批准内容、实际数据链路、视觉、操作、接收、SEO/GEO/Schema、共享回归和scope隔离的本页适用范围。静态/模拟/真实运行、界面成功/实际接收、预览/生产不能互相冒充；允许后置的发布条件单列。旧运行证据只在版本及影响范围可以证明时继承，不能把旧证据直接挂到新实现。策划侧不实施开发或修复；Gate 10另按有效明确授权执行。

## 11. 来源维护、并行修改与回退

Skill维护方法，阶段Agent/基线维护该阶段如何消费，页面Manifest维护获批组合；共享Skill只保留一个当前方法源，各消费基线独立记录其同一精确身份，不借用另一Gate的Manifest作为方法hash权威。

修改前读回当前文件及原批准记录并保存逐字节快照；写入前核对源未变化，变化则重新读取、合并有效修改。不得整份恢复覆盖别的任务更新。先定稿角色、方法与依赖，再计算完整身份、更新阶段基线及导航，并复核链接和哈希；文件存在或hash一致不等于行为通过。历史页面不批量升版、重画或重标状态。
