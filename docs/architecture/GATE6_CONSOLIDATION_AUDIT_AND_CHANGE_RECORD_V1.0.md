# Gate 6/7合并：全库盘点与同步记录 V1.0

## 1. 结论与决定

2026-09-07，用户确认原Gate 7策划交付职责可并入Gate 6，并要求检查全项目Gate描述、一次性解决。决定对象和原话见[Gate工作流V2.0](GATE_WORKFLOW_V2.0.md)§1、§8。

当前流程：`Gate 0 → 1 → 2 → 3 → 4 → 5 → 6 → 8 → 9 → 10`。

- Gate 6：策划总审、问题关闭、唯一批准交付包与Gate 9接受条件。
- Gate 7：历史编号，不再单独执行或设岗。
- Gate 8：开发方检查现有WordPress＋Next.js基线、完成技术承接、实现、测试、回执与修复。
- Gate 9：对指定实现版本独立只读验收；Gate 10单独发布授权。

这次是规则与入口迁移，不是页面阶段执行；未改变页面事实、批准进度、已封存包或开发实现，也未派发外部任务。

## 3. 实际发现的冲突

1. 根AGENTS仍定义6总审、7交付，并要求在Gate 7登记依赖。
2. 治理细则将6/7列为连续独立阶段；完成定义同时要求交付包审查，存在审查与编制分离的重叠。
3. 通用Brief模板生成独立Gate 7批准行，并把交付和运行验收混在同一检查节中。
4. 产品SOP与单型号清单把Gate 7四件套作为单独阶段；其中完整内容payload、隔离及回归要求仍必须保留。
5. Gate 5角色及设计历史提到后续Gate 7包；源文件已被批准/受测，不宜为流程编号改写受测字节。
6. 大量已批准页面有`GATE7_*`文件名、hash、Review ID和开发回执。全库替换会破坏真实历史、契约身份及Gate 9输入。
7. PRD V0.4未发现与本次合并冲突的编号Gate定义，无需为消除无关“阶段”词语升级PRD。
