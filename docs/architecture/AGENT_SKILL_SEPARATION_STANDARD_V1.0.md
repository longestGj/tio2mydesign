# Agent 与 Skill 分工标准 V1.0

## 1. 决定与适用范围

- 状态：`APPROVED_PROJECT_STANDARD / ACTIVE`。
- 用户批准与记录日期：2026-09-06。
- 决定来源：用户认可 Agent 与 Skill 分工解释，并明确要求“把这个规则写保存成文档”，随后开始设计 Gate 1 Agent。
- 批准对象：本文件规定的角色、方法与项目数据分层，以及执行、自检、独立审查的职责边界。
- 适用范围：本项目后续各 Gate 的 Agent / Skill 设计与修订。
- 不包含：对具体 Agent 详细设计的预先批准、自动创建运行任务、部署配置，或任何页面的下一 Gate、开发与发布授权。

本标准补充根 AGENTS.md 与当前已批准 Gate 标准，不增设 Gate，不替代现有审批流程。

## 2. 三类内容分别放在哪里

| 对象 | 回答的问题 | 应包含 | 不应承担 |
|---|---|---|---|
| Agent | 谁对结果负责，如何组织与判断？ | 角色、目标、任务范围、权限、上下文获取、方法选择、结果整合、返修、自检、提交和停止条件 | 把全部研究方法复制成一份巨大角色说明；自行授予批准权 |
| Skill | 某项工作怎样做好？ | 适用条件、输入、方法步骤、判断标准、输出、失败处理与示例 | 独立负责项目进度、决定用户授权、维护某页当前事实与批准状态 |
| 项目资料 | 这个项目现在是什么，用户决定了什么？ | PRD、Brief、页面身份、事实与来源、用户决定、当前版本、审查和批准记录 | 把动态事实写死在通用 Agent 或 Skill 中 |

工具是实际读取、检索、计算或写入的能力，不等于 Agent，也不等于 Skill。Agent 依据授权使用工具，并可按 Skill 的方法完成工作。

本标准是本项目的职责设计规则，不声称任意平台上的配置文件会自动建立这些权限或质量保证。

## 3. Agent 负责结果与判断

Agent 应负责：

1. 明确本次任务要交付的结果、已有授权和停止位置。
2. 找到当前有效输入，识别历史版本与资料冲突。
3. 根据页面和买家问题安排工作，选择必要的方法，而不是机械执行所有 Skill。
4. 判断研究发现意味着什么、哪些内容值得保留、哪些问题需要继续查证或交给用户决定。
5. 把多个方法的输出整合为连贯、可追溯的交付物。
6. 自检、处理返修，并向有权审查的人或任务提交成果。

Agent 的判断权限来自当前任务与项目规则，不来自角色名称。称为“负责人”不能获得额外批准、跨页修改或发布权限。

## 4. Skill 负责可复用的方法

Skill 应围绕一个有意义、可复用的能力划分，而不是围绕某个页面或每天的进度划分。

- 搜索意图分析、问题驱动研究、声明与来源核验等，可以作为候选能力。
- 同一方法可以被不同 Gate 的执行 Agent 或审查 Agent 使用。
- 不要求一个 Gate 对应一个巨型 Skill，也不要求每个微小步骤单独建立 Skill。
- Agent 说明只保留方法的选择条件、输入输出与交接关系；详细做法由 Skill 维护，避免两套规则同时变化。
- Skill 可以有自己的方法质量标准，但不能把“方法检查通过”写成“页面获批”。

拆分判断：负责最终交付和决策的内容放 Agent；可重复使用的做法放 Skill；当前页面的事实、决定和状态放项目资料。

## 5. 执行质量与独立审查分开

每个 Gate 按两个维度设计：

1. 执行 Agent：怎样把工作做好，怎样在提交前发现自身问题。
2. 审查 Agent：怎样依据原始要求、权威输入和实际成果，独立发现遗漏、错误与越界。

执行 Agent 的自检不是独立审查，不能仅切换称呼就为自己的结果授予独立 PASS。审查 Agent 可以复用底层核验 Skill，但不能只接受执行方的检查数字或总结，应核对实际成果及依据。

两种角色的批准权限继续遵守项目治理。设计了独立审查角色，不等于已授权启动新的任务、并行 Agent 或自动批准下一阶段。

## 6. 规则、事实与授权的继承

- 每次任务从当前项目资料加载页面身份、用户决定、事实和版本，不在通用角色或方法里固定型号数量、关系计数或当前批准状态。
- 继承用户已经明确作出的决定，不重复索取同一授权，也不扩大其适用范围。
- 证据缺口按根 AGENTS.md 第 2.6 节处理，不得把“资料库未找到”自动推导为“企业没有”或“禁止公开”。
- 内部核验与治理状态保存在项目资料中，不自动进入买家文案。
- 需要用户决定时，直接在对话中给出具体内容、影响与建议，并把决定写回项目文件。
