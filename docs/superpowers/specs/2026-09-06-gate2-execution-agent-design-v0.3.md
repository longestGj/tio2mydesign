## 2. 岗位定位

### 2.1 核心目标

把 Gate 1 已确认的读者任务、研究结论和事实边界，组织成买家能高效使用的网页：以尽可能少的必要阅读、选择和操作，帮助读者作出正确决定并完成本页任务。CTA、链接、SEO、GEO、Schema 与正文保持一致，形成可供 Gate 3 使用的真实内容基线。

对读者而言，页面应说明：这与我的需求有什么关系、我可以据此判断什么、依据和适用条件是什么、下一步可以做什么。涉及请求或提交时，还要说明提交后会发生什么。

Agent 对整页的内容取舍、顺序、表达质量和交付一致性负责。它需要把多个研究答案组织成一条阅读路径，而不是按研究报告章节逐段改写。不同页面类型依各自读者任务和已批准 Playbook 组织内容，不预设统一模块数或文章长度。完整性以任务能否完成衡量；研究问题、证据类别和内部检查项不自动各自成为网页模块。

### 2.2 六项职责

| 责任 | 必须作出的判断 |
|---|---|
| 承接已确认方向 | 哪些结论与用户要求必须继承，哪些局部问题仍需补查，当前允许推进到哪里 |
| 确定内容重点 | 首屏应让读者理解什么，哪些问题需要完整回答，哪些只作简要说明并引导到其他页 |
| 组织阅读顺序 | 每个模块解决什么判断，为什么放在这里，与前后模块如何衔接 |
| 完成真实文案 | 标题、正文、表格、问答、按钮及适用状态是否具体、清楚、有依据且没有机械重复 |
| 对齐行动与机器表达 | CTA、目标、预填信息、内链、SEO、GEO、Schema 是否与可见内容及批准范围一致 |
| 整合、自检与返修 | 方法输出是否解决问题，整页能否交给下一阶段，修改是否同步覆盖受影响位置 |

### 2.3 判断权限与相邻职责

- Gate 1 提供读者、问题优先级、研究答案、依据、职责边界及行动建议；Gate 2 对据此提出的实际 H1、模块顺序、完整文案与内容关系负责。上游建议若已获具体批准，按其范围继承。
- 在页面合同内可以提出表达、内容组织和行动路径方案；改变已批准方向、身份、URL、主关键词、事实或跨页职责时，按项目变更流程处理。
- 新出现的局部内容问题可定向补查；发现核心方向或关键研究结论不足时，交回具体问题、影响与建议，继续完成不受影响的部分。不能无故重开整套 Gate 1，也不能为写完文案自行补造事实。
- 跨页申请由相应转化页负责。上游页面定义买家意图、需要传递的上下文和期望体验，消费已确认的表单合同；未确认时不得自行锁定单/多 Grade、单/多文件类型、具体参数格式或后台数据结构。多产品、多文件申请是应检查的实际需求场景，不因本次讨论自动成为已实现功能。已有正式合同与新需求冲突时提交定向变更，不自行改写另一页。
- Gate 3 负责响应式线框。Gate 2 定义内容和交互语义，提供真实文字、顺序与条件；不提前决定像素布局，不以短占位掩盖长内容。
- 执行 Agent 自检并提交；独立审查与用户批准由相应责任方完成。本任务设计自己提出的角色时，也不将自身检查称为独立审查。

## 3. 输入承接建议

执行时先按根规则读取适用资料，并从当前索引和页面 Manifest 定位权威输入，不在通用角色里固定某页事实或版本。

| 输入 | Gate 2 需要得到什么 |
|---|---|
| 页面身份、完整 Brief、关键词归属、Playbook | 为谁写、负责什么、必须包含与排除什么、语言与页面类型要求 |
| Gate 1 综合研究与意图确认 | 重要问题、结论与理由、内容重点、下一步行动及尚未解决的问题 |
| 命题证据登记与用户决定 | 每个拟用事实的准确含义、来源、日期、适用范围和已批准表达 |
| 当前 Manifest 与阶段授权 | 实际有效组合、历史关系、已确认骨架或文案，以及本次停止点 |
| 相关共享合同与相邻页面 | 可用的内链、CTA 与预填约定、共享导航及法律内容责任；只读取本页涉及部分 |

接收后区分“直接继承”“局部补查”“存在冲突或需决定”。Gate 1 报告已保存不等于内容充分；应实际阅读其结论及所引用的关键依据。历史等价成果可以按文件与章节映射消费，不要求重做为新格式。

正常进入 Gate 2 的依据是有效页面合同、Gate 1 确认/批准记录及 Gate 2 授权。已存在的连续授权按原范围执行，不再次索取相同许可；不把研究内容认可自动解释为下一阶段授权。

## 4. 两次交付的工作建议

两次确认来自现行 Gate 标准，不新增 Gate 编号；以下细化其内容负责人职责。

### 4.1 先提交内容骨架

形成可在对话中直接判断的骨架：

- 拟用 H1 与 Hero 核心信息。
- 完整模块顺序、每个模块的一句话目的及其要回答的问题。
- 主次 CTA 的具体文案、目标 URL 和所需上下文；无次 CTA 时明确无。
- SEO Title、Meta Description 与 Canonical 方向。
- GEO / Schema 拟表达的实体与关系。
- 会影响取舍的具体事实待决项、条件模块与必要内部限制。

Agent 先写出本页买家任务路径，再据此解释模块先后和取舍。对作用重复的模块考虑合并；只供少数读者查阅的细节考虑下沉；不贡献必要判断或行动的内容考虑删除。不能只为让主页面显短而把重复内容全部塞进折叠区。模块应帮助读者形成判断或完成行动；某项批准内容必须保留时，安排合适位置而不擅自删除。不能先套固定模块再倒推问题，也不能因尚缺完整正文而禁止骨架送审。

骨架确认后才完成整页正文。已确认骨架仍有效时直接复用；如需改变已批准核心信息、模块顺序或职责，说明具体影响并按范围重新确认。

### 4.2 完成全文与内容合同

在已确认骨架上完成：

- H1、Hero、所有模块标题与真实正文，以及适用的表格、简明答案、FAQ、来源和日期。
- CTA 文案与目标、上下游内链、面包屑及必要帮助说明；预填字段按当前已确认合同引用，未确认时说明需要传递的上下文与待协调项，不提前硬编码。
- 本任务若负责表单页，在其获授权范围和当前合同内定义标签、输入需求及适用状态文字；已有批准合同直接继承，未决字段及单/多值需求作为具体体验决定提出。上游说明页只定义申请意图和需要交接的上下文，不替转化页锁定字段数量、参数格式或存储结构。
- 最终 SEO Title、Meta Description、Canonical、索引和语言方向；沿用批准策略，新增变更另行提出。
- GEO 实体、关系和答案表达；Schema 类型、字段来源、可见内容对应及条件规则。这里交付内容规格，不实现 Schema 代码。
- 正常、空值、事实受限、路由未就绪等适用条件下的内容处理。Buyer Clean Copy与内部控制说明分区，且买家版本不含治理占位。route/readiness、availability hold、source context等记录在内部合同；controlled request不能直接作为对买家的默认表达。只把帮助读者理解与操作的必要说明用自然语言呈现。

对企业事实继承用户已有批准，缺证按根规则提交具体事实确认。核对命题的对象、限定条件和关系，不能把一个型号的说明扩成全部产品能力，或在标题、按钮、Meta、Schema 中暗中扩大正文含义。

按完整网站的最终体验设计。共享页面或路由未完成应登记后续交付依赖，不自动删除合理 CTA，也不承诺尚未批准的响应时限、库存、文件或服务。

### 4.3 成果组织建议

| 交付职责 | 内容 |
|---|---|
| 内容骨架 | 页面核心信息、模块目的与顺序、行动和 SEO/GEO 方向，以及对应确认记录 |
| 完整买家文案 | 所有实际可见内容与适用状态文字，使 Gate 3 能直接使用真实内容 |
| 内容关系与一致性合同 | CTA/URL/预填、内链、SEO/GEO/Schema、事实对应和条件规则 |
| 当前基线导航 | 在本页唯一 Manifest 中映射有效成果、批准范围、历史版本、开放项与下一阶段权限 |

这是职责划分，尚不锁定文件数量、命名或字段模板。内容关系合同可以是现有内容架构文件中的明确章节；不为凑文件复制正文和证据。原有 Brief、命题登记及共享事实源按需要更新或引用，不能重建竞争权威。正式内容进入页面规划目录，实际位置依页面当前合同和目录规则确定。

## 5. 质量评估：买家能否高效完成任务

### 5.1 已确认的主轴

2026-09-06用户明确指出Gate 2过度工程化，并给出核心标准：

> 它不是在证明“我们考虑得很完整”，而是在证明“用户能不能用最少步骤做出正确决定并完成申请”。

这是本轮用户给出的质量方向，替代V0.2把多个检查维度平铺的提案。对非申请页面，按当前Brief映射为选择、比较、理解或其他本页任务，不把所有页面改为表单页。

“最少步骤”关注不必要的阅读、重复选择、重复输入及跳转。不能靠删掉必要说明、增加隐蔽操作或把内容塞进折叠区，换取表面上的短页面或少模块；必要的比较和解释应保留。事实准确和SEO/GEO一致性仍是支撑正确体验的底线，不以此另增买家模块。

### 5.2 Agent需要作出的四项质量判断

| 判断 | 检查实际成果时要回答的问题 | 不合格信号 |
|---|---|---|
| 路径与模块是否必要 | 买家从进入到完成本页任务怎样走？每个模块帮助哪一步？合并或删除后会损失哪个必要判断？ | 同一结论反复解释；主任务被长文章、FAQ或无关信息打断 |
| 买家内容是否干净易懂 | 只看网页文案，买家是否知道能做什么、需要什么和下一步？内部控制是否留在内部合同？ | controlled request、route readiness等项目术语成为标题、帮助文案或默认免责 |
| 名称是否符合行为 | 标题、选择器和按钮让买家预期什么？真实目标或已确认流程是否兑现这个预期？ | 只有申请上下文却称“找到文件”；申请入口写成“下载”；提交成功说成请求已批准 |
| 上下文与页面责任是否恰当 | 本页需要收集或传递什么意图？是否要求重复填写？是否未经确认限制多产品、多文件需求，或越权锁死下游结构？ | 上游页自行定成单Grade、单文件；用参数限制倒推买家只能这样申请 |

上述为角色的结果检查要求提案。详细检查方法以后按实际复用价值放入Skill；不要求为每个问题建立新文件、表格或打分字段。

### 5.3 DOC-TDS：用户给出的设计示例与决定

用户期望的任务链为：

**我需要哪类文件 → 哪个产品/Grade → 需要补什么上下文 → 提交申请。**

它是跨页任务链，不表示必须在DOC-TDS内实现四步表单，不改变CONV-DOC的申请职责，也不强制做成四个模块或四次点击。信息说明、上下文选择与正式提交怎样分配，依当前页面分工及已确认合同处理。

用户指出的具体问题及处理方向：

- Quick Choice、Comparison、TDS Scope、SDS Scope、COA Scope若反复回答“TDS看技术、SDS看安全、COA看批次”，应考虑合并为一次清楚的文件选择说明。仅有独立使用价值的细节再下沉；不是保留全部模块后只缩短措辞。
- 内部控制记录与Buyer Clean Copy分离。申请所需的“应用、目的地或文件用途”等买家信息可用自然标签呈现，不直接叫source context；内部处理状态不因改成英文短语就成为买家所需内容。
- 用户明确提出用 **Add Product Grade to Your Request** 替代 **Find Documents by Product Grade**，对应“将Grade带入申请”的行为。本设计记录该具体表达及语义方向为用户决定；不把它扩成已建立公开文件inventory。
- 用户要求考虑一次申请多个Grade、多个文件的真实需求。Gate 2先定义意图及上下文；只有表单合同正式确认后才继承相应字段单/多值约定。不会因为本示例自动修改CONV-DOC合同。

以上案例来自本轮用户陈述，不是本任务对DOC-TDS当前Manifest或运行页面完成了独立复验。本轮落实于Agent设计；DOC-TDS正式页面成果、Manifest、历史Gate批准和下游表单仍未在本任务中修改。

### 5.4 如何检查与形成结论

骨架阶段先只看拟呈现给买家的标题、模块内容要点、操作和目标，沿批准的任务路径检查是否有阻碍、重复或误导。全文阶段用全部真实文字和适用状态重复检查，不能用内部说明替页面补答案。再对照证据、用户决定、页面归属及SEO/GEO/Schema，核对正确性与一致性。

对每项需要修改的问题，给出“实际位置/原文 → 买家会怎样理解或被迫多做什么 → 影响 → 建议合并、下沉、删除或改写”。AI走查中的理解与行为预期应标明是审查推断，不冒充真实客户测试。无需为每个无问题段落制造证明材料。

执行Agent自检并修订，独立审查者读取实际作品和原始要求作出判断；自检不是独立PASS。遵循既有阻塞、重要、建议分级，不用总分抵消事实错误或任务障碍。内容存在但无法高效使用，也可以构成需要返修的实质问题。

可以建议通过当前阶段的条件是：核心任务路径清楚，必要答案和行动足够，已发现的实质重复、误导和越界问题处理完成，剩余意见不妨碍任务完成且有明确处理。既有用户确认和Gate批准流程保持；关键未决应提交具体决定，不假称已完成，也不阻塞无关工作。

### 5.5 后续验证重点

用真实任务检查方法是否能发现重复解释、内部术语外露、名称与行为不符、跨页表单过早定型；同时检查精简是否造成重要答案丢失、更多跳转或重复输入。合格作品不应只因审查者风格偏好被反复返修。

行为验证仍待开展；不能把文件结构校验、AI走查或小样本表现说成已验证真实客户效率、转化率或搜索表现。本节未启动新的Agent、Skill或页面试跑。

## 6. 方法选择、交接与返修建议

方法优先解决任务路径、内容取舍与去重、买家表达及名称与行为一致等实际问题；有具体缺口时再组织必要的事实或机器表达核验。它们是能力需求，不代表要创建五个 Skill，也不代表已有同名方法可调用。

Agent 按真实缺口选择方法，明确输入、预期结果和文件交接位置。适用 Skill 若保存支持成果，应明确实际输出合同；建议继承“保存并读回 → 返回路径/摘要/未完成项 → Agent 实际读取后综合”的方式。该建议对未来 Gate 2 Skill 的具体接口仍待设计，不扩改现有 Gate 1 Skill。

返修沿“意见涉及的命题或结构 → 可见文案 → CTA/链接 → SEO/GEO/Schema → 当前基线”检查影响，只修改受影响范围。事实问题补核依据，方向问题提交具体决定，表达问题在授权内修订。保留历史批准源，受影响的批准范围升版本，不用旧自检覆盖新改动。

执行交付以保存、读回、自检并提交为终点，使用 `DRAFT_FOR_PROJECT_CONTROL_REVIEW`。用户确认、独立审查结果及下一 Gate 权限分别记录；不得自授批准或启动后续阶段。

## 7. 本轮讨论焦点与后续设计
