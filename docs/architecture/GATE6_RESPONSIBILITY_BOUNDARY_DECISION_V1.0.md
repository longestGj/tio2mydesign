# Gate 6职责边界决定 V1.0

日期：2026-09-21。决定ID：`G6-BOUNDARY-20260921`。状态：`USER_APPROVED / ACTIVE`。

## 批准来源与范围

用户询问Gate 6是否过度要求开发；在收到四处边界修订和四项交付内容建议后明确回复“同意”。本决定据此修订通用Gate 6职责与交付方法，作为工作流V3.4、Gate 6执行合同V1.2及总控派发/接收的现行边界增补。下一次相关任务由根规则及索引读取本决定和新基线；仅沿用旧合同入口不能恢复被本决定收紧的职责。

## 职责与交付

Gate 6将已批准的内容和设计整理成一致、完整、可开发、可验收的交付依据，明确必须实现什么、怎样算符合要求；Gate 8决定如何实现，Gate 9独立核验实际实现。

| 交付内容 | 必需信息 |
|---|---|
| 批准依据 | 唯一批准组合、真实文案、冻结设计及依赖、适用共享合同；引用原源 |
| 交付一致性 | 跨合同冲突、遗漏、含义不清及处置；继承有效上游结论 |
| 依赖与责任 | 本页/共享/接收方责任、开放项、失败行为和验证阶段 |
| 验收条件 | 批准要求对应的可观察结果、稳定ID、必要证据与不通过条件 |

四部分可同处一个入口，不强制四份文件或固定条数。不重做已有效覆盖的文案、完整视觉和响应式审查；新增实质交付合同的不同作者独立复核保持。

## 四处边界修订

1. 通用角色不指定WordPress、Next.js、CMS或其他技术栈的系统分工。框架、存储、生产模型、API、组件拆分、代码路径、缓存、构建与测试实现由开发选择。已有明确批准的项目技术约束按当前有效范围继承，不因本决定取消或更换项目架构。
2. 内容映射表达批准的内容含义、关系和业务输入，不替代生产模型。缺失业务规则交原内容/产品/接收合同责任方按原批准权限确认，技术参数交开发；Gate 6不得自行补造。接口不足时说明语义差异与要求达到的结果，由开发决定适配方案。
3. Gate 6交付后负责解释、变更留痕和问题协调。Gate 8实现与测试；Gate 9承担实际实现的独立只读验收。规划规格通过不能冒充运行通过。
4. 必要证据须识别实际被测版本、可访问结果和业务语义。共用证据Manifest、预检脚本和生产规则引用当前适用Gate 8→9协议，不每页增设一套。本次不修改或撤销该协议。

批准文案、设计、响应式和状态、共享消费、适用隔离、行为与错误/成功含义、发布条件仍须完整交付。例：批准合同要求真实接收确认后才能显示成功，Gate 6必须保留该条件；服务选型和测试框架由开发决定。未来实现尚未完成不自动阻断交付，未明确的必需业务规则不能伪装就绪。

## 生效、影响与回退

当前组合见[基线V1.3](GATE6_AGENT_SKILL_CURRENT_BASELINE_MANIFEST_V1.3.md)。同步Agent V0.9、交付Skill V0.5、根阅读路由、索引及角色/方法目录；一致性Skill V0.4、执行合同V1.2和接收合同V1.1原件保留，与本增补共同消费。

本次不改变任何页面批准组合、状态、开发/外发/发布授权，不批量撤销已批准技术约束，不修改其他任务的架构迁移。历史包在下次获授权修订时按本边界处理；发现实际冲突记录责任与影响，不静默覆盖。

风险：将“实现自主”误读为可以忽略批准结果或必要证据；由来源—交付—验收双向核对与既有独立复核控制。回退需对应有效决定，按[文件变更清单](../../90_archive/project-governance/2026-09-21-gate6-responsibility-boundary/file-changes.json)恢复本轮段落与指针，保留并行修改和历史批准。
